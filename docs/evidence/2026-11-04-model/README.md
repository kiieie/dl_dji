# 2026-11-04 설비 탐지 모델(facility_v1_coco) 변환·정확도 확인

사용자가 학습한 모델은 YOLO11l, imgsz 1280, 4종(COS·LP·SUS·LA)이다. 원본 가중치는 `models_src/`(git 제외)에 있다.

변환은 두 단계로 했다.
- ONNX: 기존 `D:/kiie/projects/inspection/.venv`의 Ultralytics 8.4.50을 썼다.
- tflite: `build/yolo-export/venv`의 tensorflow 2.19 + onnx2tf 1.20으로 fp16을 만들었다(`tools/export_facility_model.py`).
- 결과는 `build/models/facility-v1-coco-{640,960,1280}-fp16/`(각 약 50MB)이다.

## 정확도: 원본(.pt, 1280)과 일치율

- 사진: 11-03 대평선 #19·#20 실제 사진 80장(광각, 27m, 전주에서 10m 사선)
- 도구: `tools/compare_facility_models.py`
- 일치 기준: 같은 클래스이고 IoU 0.5 이상

| 모델 | 입력 | 재현율 | 정밀도 | PC 시간/장 |
|---|---|---|---|---|
| tflite 1280 | 전체 사진 | 0.85 | 0.89 | 803 ms |
| tflite 960 | 전체 사진 | 0.60 | 0.71 | 433 ms |
| tflite 640 | 전체 사진 | 0.05 | 0.33 | 206 ms |
| tflite 960 | 가운데 50% 크롭 | 0.71 | — | 528 ms |
| tflite 640 | 가운데 50% 크롭 | **0.88** | — | 299 ms |
| tflite 640 | 가운데 70% 크롭 | 0.61 | — | 315 ms |

- 크롭 행의 재현율은 크롭 안에 있는 기준 상자(20개 중 17개)에 대한 값이다.
- 가운데 50%를 640으로 돌리면 픽셀 밀도가 전체 1280과 같다. 그래서 **비행 중 실시간 표시는 640 모델 + 가운데 50% 크롭**으로 한다. 사진은 전주를 겨냥하므로 설비는 대부분 가운데에 있다.
- 착륙 뒤 정밀 탐지는 1280 전체 사진으로 한다.
- 표본이 작다(80장에서 기준 상자 20개). 수치는 방향을 정하는 근거로만 쓰고, 다음 현장 사진으로 다시 잰다.

## 알게 된 것
- **원본 모델도 이 사진에서는 거의 못 찾는다**(80장에 상자 20개, conf 0.25).
  - 학습 사진(DPS-137L)보다 우리 광각 사진에서 설비가 훨씬 작게 찍힌다(27m, 사선 10m).
  - **망원(7배) 사진**이 이 모델에 맞는다. 망원 촬영 동작(5.6, 2026-11-04 구현)이 들어가면 망원 사진으로 다시 잰다.
- 1280 tflite가 원본과 다른 2건은 LP 2개다. fp16 변환이나 레터박스 차이로 보이며, 표본이 작아 판단을 미룬다.
- 외부 측정 도구는 실행 허가가 없어 쓰지 않았고, 앱 안 측정 기능으로 쟀다(아래).

## 조종기(RC Pro, Snapdragon 865) 시간: 앱 안 측정

- 실행: `adb shell am start -n kr.co.dl_dji/com.example.myfirstapp.MainActivity --es bench all`
- 원본: `bench-20261104-110204.txt`
- 사진: 모의 비행 사진 6.8MB 1장(시간 측정용)
- 방법: 2회 예열 후 10회의 평균. 단위는 ms. 전체 = 디코딩 + 전처리 + 추론 + 후처리.

| 모델 | 처리 | CPU 4스레드 전체 | GPU 전체 | GPU 추론만 |
|---|---|---|---|---|
| 개발용 COCO 11n 640 | 전체 사진 | 341 | 187 | 43 |
| 설비 11l **640** | **가운데 50%** | 2511 | **431** | 269 |
| 설비 11l 640 | 전체 사진 | 2489 | 408 | 268 |
| 설비 11l 960 | 전체 사진 | 5538 | 679 | 494 |
| 설비 11l **1280** | **전체 사진** | 9821 | **1194** | 976 |

- **GPU가 CPU보다 8~10배 빠르다.** CPU만으로는 11l을 쓸 수 없다(1280 1장 9.8초).
- 비행 중 실시간(640 + 가운데 50%): 1장 0.43초. 사진 간격(약 6초)보다 훨씬 짧다.
- 착륙 뒤 정밀(1280 전체): 1장 1.2초. 사진 80장이면 약 1.6분이다.
- 연속 30회(640 + 크롭, GPU): 0.43초를 그대로 유지했다. 발열 상태 0(없음)에서 바뀌지 않았다.
- 디코딩은 0.11~0.16초다. `inSampleSize` 축소 디코딩이 동작한다(1/8~1/2).
- 영상(FPV) 위 실시간 표시(9.6 2단계)의 조건(0.5초 이하)을 640 + 크롭이 만족한다. 다음 단계로 진행할 수 있다.

## 최적화 뒤 (9.7, 같은 사진, GPU)

| 경로 | 전 | 후 |
|---|---|---|
| 실시간 640 + 가운데 50% | 431 ms | **286 ms** |
| 정밀 1280 전체 | 1194 ms | **1062 ms** |
| 가운데 영역만 디코딩(640 크롭) | 143 ms | 61 ms |
| 전처리 1280 / 640 | 72 / 19 ms | 20 / 6 ms |

- 원본 파일: `bench-20261104-121702-opt-cold.txt`(캐시 없음), `bench-20261104-122633-opt-warm.txt`(캐시 있음)
- 연속 30회: 286 ms를 유지했다. 발열 변화는 없었다.
- 로그에서 GPU는 OpenCL로 돌았다("Initialized OpenCL-based API"). 두 번째 실행에서는 "from serialized data"로 나와 셰이더 캐시가 동작했다.
- **문제: 캐시 없이 처음 열 때 매우 길다.**
  - 지속 성능 옵션 때문에 처음 열 때 GPU 커널을 튜닝한다. 640은 60초, 960은 331초, 1280은 429초가 걸렸다. 캐시가 생긴 뒤에는 약 0.2초다.
  - 캐시를 `codeCacheDir`에 두면 앱을 업데이트할 때마다 지워진다.
  - 그래서 캐시가 없으면 빠른 옵션으로 먼저 열고, 땅에 있을 때 뒤에서 캐시를 만들도록 고친다(9.7).
- INT8(640 + 크롭, 현장 사진 85장으로 보정)
  - 정수 양자화는 재현율 0.00이다. 상자 좌표(픽셀)와 점수가 출력 텐서 하나의 int8 눈금을 같이 써서 점수가 뭉개졌다.
  - 가중치만 INT8은 재현율 0.88이지만, Android 10 NNAPI와 GPU 어느 쪽에서도 더 빠르지 않다.
  - **채택하지 않는다.** 더 빠르게 하려면 11n 재학습이 낫다.

## 최적화 뒤(9.7, 같은 날 오후): `bench-a-sustained.txt`

- 적용: GPU `SUSTAINED_SPEED` + 직렬화 캐시, 가운데 영역 디코딩, 전처리 버퍼 재사용(9.7 O1·O2·O3·O7). 사진은 모의 비행 사진이라 상자 0개다(시간만 봄).
- 비행 중 1장(640 + 가운데 50%, GPU): 431 → **286 ms**(디코딩 143→61, 전처리 19→6, 추론 269→219).
- 착륙 뒤 정밀(1280 전체, GPU): 1194 → **1062 ms**(전처리 72→20, 추론 976→892). 960 추론 494→453.
- 연속 30회: 285~287 ms, 발열 0 그대로.
- **캐시 없이 SUSTAINED로 처음 열기: 640 60초, 960 331초, 1280 429초**(커널 맞추기). 캐시가 있으면 약 0.2초. 그래서 두 단계 열기(9.7 O2')로 바꿨다.
