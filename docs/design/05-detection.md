## 9. 탐지(YOLO) 설계

### 9.1 모델 규격 (앱 ↔ 모델 계약)

**앱은 아래 규격만 따르면 모델을 교체해도 동작하도록** 설계한다. 첫 실제 모델은 사용자가 학습한 설비 탐지 모델(YOLO11l, COS·LP·SUS·LA, 2026-11-04)이다(9.6).

```
models/<version>/
├── model.tflite     # YOLO(v8/11 계열) TFLite, float16 또는 int8
├── labels.txt       # 클래스 이름 한 줄에 하나
└── model.json       # 메타데이터
```

```json
{
  "version": "2026.10-dl-v1",
  "architecture": "yolo11n",
  "input": { "width": 640, "height": 640, "format": "RGB", "normalize": "0-1" },
  "output": { "layout": "1x(4+C)x8400", "nms": false },
  "thresholds": { "score": 0.35, "iou": 0.5 },
  "alertLabels": ["bird_nest", "foreign_object"],
  "role": "live",
  "displayNames": { "bird_nest": "조류 둥지" }
}
```

- `role`(선택, 2026-11-04): `live`(비행 중 최근 1장, 작은 입력) 또는 `full`(착륙 뒤 정밀). 없으면 옛 모델로 보고 두 칸 모두의 후보가 된다(9.6).
- `displayNames`(선택): 라벨 → 화면 이름. 판독·앨범·카메라 뷰 상자에 쓴다. 없는 라벨은 라벨 그대로 보인다.

- `alertLabels`에 해당하는 클래스(검출 대상)가 탐지되면 검출음을 내고 "검출"로 표시한다. 그 밖의 탐지(설비 등)는 저장하고 사진에 표시하지만 검출로 세지 않는다(`DETECTION.alert`).
- 모델을 가져올 때 입력과 출력 텐서 모양을 검사하고, 규격이 맞지 않으면 거부한다. 입력은 `1×H×W×3` float32, 출력은 `1×(4+C)×N` float32이고 `C`는 `labels.txt` 줄 수와 같아야 한다. int8 모델도 입출력은 float32여야 한다(Ultralytics 내보내기 기본).
- 출력의 상자는 입력 이미지 크기 대비 0~1 비율의 `cx, cy, w, h`다(Ultralytics TFLite/LiteRT 내보내기 기본). 픽셀 단위 모델이면 `"output": { "boxes": "pixel" }`로 적는다.
- **모델 위치**: 앱 폴더의 `models/<version>/`이다. ⑥ 설정의 [모델 폴더 가져오기]로 넣거나(F-18), 개발 중에는 adb로 넣는다. ⑥ 설정에서 모델마다 [비행 중]·[정밀]을 고른다. 고르지 않았으면 `role`로 자동으로 고른다(비행 중: `live` 중 입력이 가장 작은 것, 정밀: `full`, `full`이 없으면 비행 중 모델이 정밀도 맡음, `core/detect` `ModelPick`). 고른 모델이 열리지 않으면 다음 후보로 간다. 모델이 하나도 없으면 모의 탐지기(`FakeDetector`)를 쓴다.
- **설비 모델(2026-11-04)**: `tools/export_facility_model.py`로 원본 가중치(`models_src/`, 저장소 제외)를 fp16 tflite 640·960·1280 폴더로 만든다(`build/models/facility-v1-coco-*-fp16/`, 640·960은 `live`, 1280은 `full`, `alertLabels: []`, 상자 픽셀 단위). 개발용 COCO `yolo11n`(`tools/export_coco_model.sh`)도 그대로 쓸 수 있다. Ultralytics 모델과 가중치는 AGPL-3.0이고 학습 데이터는 사내 것이므로 저장소와 배포 앱에 넣지 않는다(14장 미정 4).

### 9.2 탐지 대상 클래스 (초안, 학습 데이터 수집 후 확정)

**1차 목표는 객체 검출이다. 설비의 이상 유무(파손, 부식, 기울어짐 등)는 판정하지 않는다**(2026-09-29 사용자 결정). 앱은 검출 대상이 사진에 있는지만 알리고, 이상인지는 사람이 판단한다.

| 구분 | 클래스 | 비고 |
|------|--------|------|
| 검출 대상(1차) | 조류 둥지(`bird_nest`), 이물질(`foreign_object`: 비닐, 연, 현수막 등) | `alertLabels` |
| 보류 | 애자 파손·오염, 부식, 기울어진 전주, 설비 종류(전주, 애자, 완금, 변압기, COS, 피뢰기) | 이상 판정이 필요해지면 검토 |

### 9.3 추론 파이프라인

1. 이미지 디코딩: 원본(20MP)을 다 풀지 않고 `inSampleSize`로 쓸 영역의 긴 변이 입력 이상으로 남는 만큼만 줄여 읽는다(`sampleSize`). 비행 중 1장은 가운데 영역만 푼다(9.7 O1). **전체 이미지를 한 번 추론**한다(비행 중 최근 1장만 가운데를 잘라 넣음, 9.6). 타일 분할은 MVP 이후.
2. 레터박스 리사이즈(입력 크기), 정규화
3. 추론: GPU delegate(`CompatibilityList`, 직렬화 캐시, 두 단계 열기: 지속 성능 캐시가 있으면 `SUSTAINED_SPEED`, 없으면 기본으로 바로 열고 캐시는 뒤에서, 9.7)를 시도하고 실패하면 CPU(XNNPACK, 스레드 4개)로 전환한다(2026-11-04). 실제로 쓴 쪽은 운용 로그(`detect open`)에 남는다. 단계별 시간(디코딩·전처리·추론·후처리)은 로그(`Detector` 태그)와 속도 측정(9.6)에 남는다.
4. 후처리: 점수 필터 → NMS → (타일이면) 전역 좌표 병합 후 NMS 한 번 더 → 원본 좌표계로 변환
5. 결과를 저장하고 알림

- 추론은 전용 스레드 하나(`detector`)에서 차례로 실행해 비행 UI를 막지 않는다. GPU delegate는 만든 스레드에서 돌려야 하므로 모델 열기도 그 스레드에서 한다.
- RC Pro의 성능(메모리, 추론 시간)은 PoC에서 측정한다. 목표: 이미지 1장 1초 이내(1회 추론), 타일을 도입하면 4개 3초 이내.

### 9.4 구현 언어 결정: Kotlin 우선, 필요 시 C++ 부분 적용

**결정**: 탐지 파이프라인은 **Kotlin + TFLite Kotlin/Java API**로 구현한다. C++(NDK)는 측정 결과 필요한 단계에만 부분적으로 적용한다(하이브리드).

| 근거 | 내용 |
|------|------|
| 추론은 이미 네이티브 | TFLite Kotlin/Java API는 C++ 엔진(XNNPACK, GPU delegate)을 호출하는 얇은 래퍼다. 호출 비용은 1ms 미만이고 추론은 수백 ms이므로, 추론 부분을 C++로 다시 작성해도 이득이 거의 없다. |
| 실시간 처리가 아님 | 전주당 1~2장, 목표 3초. 전처리와 후처리는 Android `Bitmap` API, TFLite Support 라이브러리로 충분할 것으로 예상한다. |
| 네이티브 크래시 위험 | C++ 메모리 오류는 앱 프로세스를 종료시켜 비행 중 운용 화면을 잃게 된다. Kotlin 예외는 잡아서 처리할 수 있다. |
| DJI SDK와의 충돌 | DJI SDK가 자체 `libc++_shared.so`를 포함하고 있어 `pickFirsts`로 충돌을 막고 있다. 자체 C++ 라이브러리를 추가하면 C++ 런타임 버전이 맞지 않을 위험이 생긴다. |
| 개발 부담 | NDK/CMake, JNI, ABI별 빌드, 네이티브 디버깅이 추가된다. |

**C++ 전환 기준**

1. 탐지 기능은 `Detector` 인터페이스 뒤에 둔다. 구현(`TfliteYoloDetector`)을 바꿔도 나머지 코드에 영향이 없어야 한다.
2. PoC ⑤에서 RC Pro 기준으로 **전처리 / 추론 / 후처리 시간을 각각 측정**한다.
3. 목표(이미지 1장, 1회 추론 1초, 타일 도입 시 4개 3초)를 넘는 단계가 있으면 그 단계만 C++로 옮긴다. 후보는 YUV→RGB 변환, 리사이즈·타일 분할, NMS다.
4. C++를 도입할 때는 DJI SDK와 같은 `c++_shared` STL을 쓰고, NDK 버전 호환성을 먼저 검증한다. 네이티브 코드에서 예외가 JNI 밖으로 나가지 않게 모두 잡고, 실패는 오류 코드로 반환한다.

**재검토 조건**: 탐지 코드를 다른 플랫폼(PC·서버 재분석, iOS)에서 재사용해야 하거나 실시간 영상 분석이 요구사항에 들어오면, C++ 탐지 코어 + 얇은 JNI 구조로 다시 검토한다.

> NCNN(Tencent)과 MNN(Alibaba)은 중국 기업의 오픈소스 엔진이다. 데이터를 외부로 보내지는 않지만, 조직 정책을 고려해 사용하지 않는다(7.1).

### 9.5 학습 데이터 순환 (앱 밖)

앱이 촬영한 사진과 메타데이터를 내보낸다 → 라벨링(예: CVAT, 사내 도구) → Ultralytics로 학습 → TFLite로 내보내기 → `models/`로 배포. 모델이 없는 환경(에뮬레이터 등)은 COCO 범용 모델이나 모의 탐지기로 파이프라인을 검증한다.

### 9.6 두 단계 탐지: 비행 중 최근 1장 + 착륙 뒤 정밀 (2026-11-04)

설비 모델(YOLO11l, 입력 1280)은 개발용 11n보다 연산이 약 50배다. 조종기 부담을 줄이면서 비행 중에도 최소한의 결과를 보이려고 둘로 나눈다(사용자 결정 11-04).

| 단계 | 언제 | 무엇을 | 모델 | 저장 |
|---|---|---|---|---|
| 비행 중 최근 1장 | 사진을 저장할 때마다 | 가장 최근 사진 한 장만. 처리 중에 온 사진은 마지막 것만 남김(`LatestOnly`) | `live` 640, 사진 가운데 50%만 잘라 넣음 | 안 함(화면만) |
| 착륙 뒤 정밀 | 내려왔을 때, 앱을 켰을 때 | 최근 7일 미션 사진 중 정밀 결과가 없는 것 전부(`PreciseBackfill`) | `full` 1280, 전체 사진 | `DETECTION`을 바꿈, 사진별 `CAPTURE.detectModel`(Room 8) |

- **실행기는 탐지하지 않는다.** 방식 A 사진 일꾼은 다운로드·저장만 하고(`InspectionExecutor`), 앱이 저장한 사진을 두 단계로 넘긴다(`FlightViewModel`의 기록기 감싸기). 실시간 탐지는 기다리지 않으므로 비행 판단을 막지 않는다. 방식 B(도착 후 분석)만 실행기의 `Detector`를 쓴다.
- **표시**: 설비 4종은 이상이 아니라 설비라 `alertLabels: []`다. 회색 상자와 한국어 이름(`displayNames`)으로만 보이고 "탐지"(검출) 수에 세지 않으며 신호음도 없다. 판독·앨범에는 "설비 n"을 따로 보인다. 카메라 뷰(자동·수동)에는 미니맵 위 "마지막 사진" 썸네일(상자, 자른 영역 흐린 테두리, "LP 2 · SUS 4", 누르면 크게 이름과 함께, 10.5.2).
- **가운데 자르기 근거**(11-03 대평선 사진 80장, 원본 .pt 1280 대비 재현율, `docs/evidence/2026-11-04-model`): 전체 사진 1280 0.85 / 960 0.60 / 640 0.05, 가운데 50%를 640 **0.88** / 960 0.71(자른 영역 안 기준 상자 17개). 가운데 50%를 640에 넣으면 픽셀 밀도가 1280 전체와 같다. 기준 상자가 20개뿐이라 방향을 정하는 근거로만 쓰고, 다음 현장·망원 사진으로 다시 잰다. 비율은 `AppConfig.Detector.LIVE_CROP_FRACTION`.
- **부담 제한**(`detect/PreciseDetection.kt`, 값은 `AppConfig.Precise`): 정밀 탐지는 기체가 떠 있으면(자동·수동 비행) 쉬고 내려오면 남은 것부터 한다. 조종기 발열(`PowerManager`) SEVERE 이상, 조종기 배터리 20% 미만, 속도 측정 중에도 쉰다. 쉬면 바로, 다 끝나면 60초 기다린 뒤 모델을 닫는다(9.7 O5). 비행 중 1장도 발열 SEVERE 이상이면 쉰다(9.7 C). 진행은 판독 화면 위 "정밀 탐지 37/120 · 쉼(이유)". 실패한 사진은 그 실행 동안 건너뛴다. 앱이 비행 중 다시 켜지면(6.4) 비행 화면이 기체 상태를 알릴 때까지 쉰다.
- **속도 측정**(기체 없이, `detect/ModelBench.kt`): 검증 화면 [모델 속도 측정] 또는 `adb shell am start -n kr.co.dl_dji/com.example.myfirstapp.MainActivity --es bench all`. 모델마다 CPU 4스레드·GPU로 2번 데우고 10번 재며(`live`는 가운데 자르기도) 단계별 평균/최소/최대와 앞뒤 발열을 남기고, 비행 중 모델을 30번 연속 돌려 5번마다 발열을 남긴다. GPU는 기본(FAST)을 캐시 없이 연 시간을 재고, 지속 성능(SUSTAINED)은 캐시가 있을 때만 잰다(없으면 "캐시 없음 – 뒤에서 생성"). `--es bench full`이면 캐시가 없을 때 만들어 잰다(모델마다 1~7분). 사진은 `--es benchPhoto <절대 경로>`, 없으면 가장 최근 실제 사진(이름에 `_FAKE_`가 없는 것). 결과는 `files/logs/bench-<시각>.txt`와 운용 로그 `bench`, 증빙은 `docs/evidence/2026-11-0x-model/`.
- **실시간 단계**
  1. 사진 실시간(지금): 위 표의 첫 줄. 목표 지연은 촬영 뒤 1~3초(사진 간격 약 6초).
  2. FPV 영상 위 표시(기체가 지점에서 멈춰 찍을 때): `CameraStreamManager` 프레임을 초당 1~2장만 같은 소형 모델로 돌려 영상 위에 상자를 겹친다. 1단계 실측에서 640 모델이 GPU로 1장 0.5초 이하일 때만 하고, 설정에서 켜고 끈다.
  3. 영상 매 프레임에 가깝게: 같은 데이터로 YOLO11n/11s(입력 960)를 학습(11l에서 증류)하고 fp16 + GPU로 1장 0.1~0.3초(INT8은 이 기기에서 이득이 없어 접음, 9.7 O4). 앱은 9.1 폴더만 바꿔 넣는다(사용자 학습 필요).
- **자세(pose) 모델 후보**: 함께 받은 `pole_pose_v3b`는 쓰지 않고 보관한다. 사진 안 전주 위치·기울기로 구도를 확인하는 후보다.

### 9.7 최적화 (2026-11-04)

RC 실측(GPU, 9.6 속도 측정, `docs/evidence/2026-11-04-model`)과 PC 정확도(원본 .pt 1280 대비 재현율)를 기준으로 정했다. 단위 ms, "앞→뒤"는 최적화 전(11-04 아침)→뒤(아래 항목 적용, `bench-a-sustained.txt`).

| 경로 | 디코딩 | 전처리 | 추론 | 전체 | 재현율 |
|---|---|---|---|---|---|
| 비행 중 1장(640 + 가운데 0.5) | 143→61 | 19→6 | 269→219 | 431→286 | 0.88 |
| 착륙 뒤 정밀(1280 전체) | 143→145 | 72→20 | 976→892 | 1194→1062 | 0.85 |
| (참고) 960 전체 / 640 전체 | — | — | 494→453 / 268→222 | 679→611 / 408→351 | 0.60 / 0.05 |

- 비행 중 모델 30회 연속(GPU, 가운데 0.5): 285~287 ms, 발열 0 그대로.
- **GPU 첫 열기(캐시 없음, SUSTAINED)**: 640 60초, 960 331초, 1280 429초(7분). 커널 맞추기(튜닝) 시간이다. 캐시가 있으면 약 0.2초. 이것 때문에 두 단계 열기(O2')를 둔다.

- **GPU와 FPV가 함께 쓰는 문제**: Adreno 650은 OpenCL 커널과 GL·SurfaceView(FPV 영상) 그리기를 시분할로 돌린다. 비행 중 1장 추론(약 0.22초) 동안 FPV 프레임이 늦을 수 있다. FPV를 켠 시험 비행에서 속도 측정과 FPV 끊김을 함께 잰다. 문제가 되면 사진 간격 안에서 추론을 미루는 방법을 본다.
- **메모리**: 카메라 뷰를 열면 비행 중 모델(640)을 미리 열므로, 정밀 모델(1280)이 O5로 열려 있는 동안 둘이 함께 GPU에 있을 수 있다. 이륙하면 정밀 모델은 바로 닫힌다.
- **GPU 캐시 만들기와 이륙**: 만들기는 도중에 멈출 수 없어(640 1분·1280 7분) 그 사이 이륙하면 끝날 때까지 GPU를 함께 쓴다. 카메라 뷰가 열려 있으면 비행 중 모델이 열려 있으므로 새로 시작하지 않는다. 문제가 되면 만들기를 별도 프로세스로 옮겨 이륙 때 죽인다.
- **O4 INT8 + NNAPI: 안 함(11-04 실험)**. 현장 사진 85장(640 + 가운데 0.5, 원본 .pt 대비)에서 재현율 fp16 0.88, 전체 정수 `*_integer_quant` 0.00(픽셀 상자 0~1280과 0~1 점수가 출력 int8 스케일 하나를 같이 써 점수가 뭉개짐), 동적 범위 양자화 0.88. 동적 범위는 하이브리드 연산이라 Android 10(NNAPI 1.2, 부호 있는 int8은 1.3부터)에서 NNAPI 이득이 없고 GPU에서도 빨라지지 않는다. 채택 조건(재현율 ±0.05 안이고 RC에서 실제로 빠름)을 못 채워 접는다. 더 빠른 길은 사용자가 계획한 YOLO11n 재학습(9.6 실시간 3단계)이다.
